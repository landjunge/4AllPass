### Hardening needs (not reproduced as faults, not changed)

- **F-25 nonce budget — open, B; A before any automated writer.** See below.
- `unlockSnapshot`/`verifySnapshot` take `expectType` and `entryId` from the
  record itself. Not exploitable (wrapping keys differ per type; the manifest
  commits the entry set); manifestless legacy snapshots get no set commitment. C.
- `deriveRecoveryWrappingKey` accepts `cryptoVersion ≠ 1` (device path refuses);
  no caller passes it. C.
- Core-object envelopes ignore a falsy `kdf` on non-master kinds; the wire decoder
  refuses it; no semantic effect. C.
- `decodeEncryptedEntry` refuses an empty ciphertext, so empty plaintext does not
  round-trip; unreachable (entry plaintext is JSON). C.
- Share import decrypts wire entries, not the verified copies (F-19 pattern);
  JSON-decoded objects have no accessors. Belongs to P06.

### F-25 nonce and key lifetime (evidence, not a claim)

`vault-session.nonce-budget.test.ts` pins the rate: every commit **attempt**,
including one refused with 409, seals all N entries plus one manifest under the
Vault Key with fresh 96-bit nonces; envelopes are carried over byte-identical.
So seals(VK) = Σ over attempts (Nᵢ + 1) + creation, with N ≤ 100 000
(`MANIFEST_ENTRIES_MAX`). Attempts before the 2³² bound (collision ≈ 2⁻³³):
N = 1 000 → 4 290 676; N = 10 000 → 429 453; N = 100 000 → 42 949.
Only the PWA commits snapshots (`commitEntries`: create, import, save, device
enable); broker, sidecar, extension and backend have no seal path under VK.
Other keys seal once or a handful of times: MK (new salt per wrap), DK (new per
binding), DWK (one per enrolment), RWK (one per kit and VK generation). Nothing
counts seals or forces rotation; the revision number does not bound attempts.
